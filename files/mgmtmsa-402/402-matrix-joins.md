How a join works, before the rows below (Lecture 4): a join is two steps. First form all pairs of rows from the two tables (the Cartesian product), then filter those pairs on the join condition. The condition is written explicitly in ON. That two step picture predicts every row count in this matrix.

Cardinality, for predicting rows (Lecture 4): a 1:1 relationship gives at most one match per row. A 1:M relationship gives one row on the one side matched to many rows on the many side. An M:M relationship matches many rows to many rows, so output rows multiply. Duplicate join keys always multiply rows: a row matches every matching row on the other side, the database does not stop at the first match.

|---|---|---|---|---|
| CROSS JOIN | Every pair of rows, one output row for each combination of a row from the first table and a row from the second. Row count is the first table row count times the second table row count. | Not applicable. There is no join condition, so nothing is unmatched. Every row pairs with every row. | Almost never the right answer. Lecture 4 teaches it as an antipattern: there is nearly no reason to write a cross join. It appears when a join condition is missing or too loose, which is called a Cartesian join, runaway join, join explosion, or fanout. | Writing CROSS JOIN and then filtering with WHERE. Lecture 4 says this receives no credit. The other trap is an accidental cross join: a loose condition returns many, many more rows than wanted and can exhaust memory and crash the server. |
| INNER JOIN, equi join | Only pairs where the join key values are equal in both tables (the ON condition uses = and only =). A row that matches k rows on the other side produces k output rows, so duplicate keys multiply rows. Worked deck case: one row with A = alpha in the first table and two rows with A = alpha in the second table gives 2 output rows for alpha. | No match, no row. A row with no matching join key value on the other side is dropped from the result, from both tables. | The prompt asks for data from two tables together on the same output row, matched on a shared attribute, and only matched records are wanted. This is the most common join in the course. | Writing it any way other than explicit JOIN ... ON. Never NATURAL JOIN, never USING, never the implicit comma join. Also failing to qualify a column name that exists in both tables: that name is ambiguous and must be written with its table, as in R.A and S.A. |
| INNER JOIN, non-equi join | Pairs where the ON condition, which contains at least one comparator that is not =, is satisfied. A row that satisfies the condition against k rows on the other side produces k output rows. | No match, no row, same as any inner join. A row whose value satisfies the condition against no row on the other side is dropped. Deck example: a percentage that falls in no grade band gets no grade row. | The prompt asks to match on a range, a threshold, or an inequality instead of an exact equal value, for example assigning a letter grade from a percentage, or matching a value to the band it falls in. | Treating it as an equi join and writing only = conditions, so range matches are impossible. Also writing the range condition in WHERE after a cross join instead of in ON: that is the cross join antipattern and receives no credit. |
| UNION | Not a join. It stacks the rows of two result sets into one taller result and removes duplicates. Even if an input has a primary key, duplicates are possible in the output, because the output is a result set, not a table. | Not applicable as a join concept. There is no matching between the two sets, rows are stacked, not paired. | The prompt asks for one combined list of rows coming from two queries or two tables with the same output shape, with each distinct row appearing once. | Using UNION ALL when the prompt wants each distinct row once, so duplicates survive. Also the reverse error is in the UNION ALL row. Note: the decks state that UNION removes duplicates but do not state the stacking requirements for the two result sets (column count and type compatibility): not in held decks, verify. |
| UNION ALL | Not a join. It stacks the rows of two result sets into one taller result and does not remove duplicates. Every row from both sets appears, including rows that appear in both. | Not applicable as a join concept. Rows are stacked, not paired. | The prompt asks for one combined list of rows from two queries or two tables, keeping every occurrence, for example when duplicates are real data that must be counted. | Using UNION when every occurrence must be kept, so UNION silently deletes duplicate rows and totals come out low. ## Other join forms named but not taught in Lecture 4
The classification chart also names semi joins, anti joins, self joins, and natural joins. Of these, only the natural join is covered, as an antipattern: the database picks the join columns, the condition is invisible to a reader, and a schema change (a new same named column on both tables) silently changes the result or turns it into a cross join. Never use it.

## Rosario rules for joins (Lecture 4, verbatim in substance)
- Explicitly specify the join condition, always. Every join written in this class must be a theta join, meaning the condition is spelled out.
- Always explicit JOIN ... ON.
- Never use NATURAL JOIN.
- Never use the implicit join (multiple tables listed in FROM, the comma join).
- Never use USING. On exams the join condition must be stated explicitly, so use JOIN ... ON.
- Use the correct join type. Do not use shortcuts.
- Qualify shared column names: a column that exists in both tables must be written with its table (R.A, S.A). A column that exists in only one table does not need qualification, but qualifying is the deck's recommended habit.

## Writing strategy for a join query (Lecture 4)
Write in execution order: FROM first (where the data comes from), then JOIN (the table being joined), then ON (the join condition, with special care), then WHERE, then GROUP BY, then HAVING, then SELECT with proper aliases, then ORDER BY, then LIMIT if needed. Full writing order with joins: SELECT, FROM, JOIN, ON, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. Full execution order: FROM, JOIN and ON, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT (DISTINCT sits after SELECT per the Lecture 3 execution order; the Lecture 4 execution list runs FROM, JOIN/ON, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT).
