# 402 Matrix: Clauses and Aggregates (Lecture 3)

Sources are the Lecture 1 to 4 decks (read in full Oct 26, 2026) plus the Lecture 3 replacement pack.

| Concept | What it is | Formula or skeleton | Question cue that triggers it | Classic trap |
|---|---|---|---|---|
| WHERE | Filters rows. It pre-filters the raw rows of the table, acting on values in columns and on transformation functions applied row by row, typically not on aggregation functions. It runs before grouping, so no group and no aggregate exists yet when it runs. | WHERE <row condition>, using =, >, <, >=, <=, != (some use <>), connected with AND and OR, plus IN or NOT IN for set membership and IS NULL or IS NOT NULL for NULL tests. | The condition is about an individual row's own values, for example only public videos, only undergraduate students, only rows with gpa below 3.5 as individual records. | Putting an aggregate condition in WHERE, for example WHERE AVG(views) > 50000 or WHERE COUNT(*) > 2. It fails, because aggregates do not exist at WHERE time. That condition belongs in HAVING. Also using a SELECT alias in WHERE: aliases are created in SELECT, which runs after WHERE, so the alias does not exist yet. |
| HAVING | Filters groups. It runs after GROUP BY, once groups are formed and their aggregates are computed, and keeps only the groups whose aggregate condition holds. Deck example: majors with average GPA below 3.5. | HAVING <aggregate condition>, written with the full aggregate, for example HAVING AVG(gpa) < 3.5 or HAVING COUNT(*) >= 3. Never the SELECT alias. | The condition is about a group as a whole, for example channels with at least 3 videos, majors whose average GPA is below 3.5, channels whose total views reach a threshold. | Two traps. Using a SELECT alias in HAVING: Rosario rule, no aliases in HAVING, PostgreSQL rejects them and the standard does not allow them, so write the full aggregate again. And putting a raw row condition in HAVING that belongs in WHERE, which also wastes work because more rows reach the grouping step. |
| COUNT(*) | Counts rows. It counts every row in the set, whatever the NULLs. Deck wording on the tinybase global aggregate: counts all rows. | COUNT(*) | The question asks how many rows or records there are, for example how many videos a channel has, counting records whose measured values may be missing. | Using COUNT(column) out of habit when the question is how many rows exist, which undercounts by the number of NULLs in that column. On the replacement pack dataset, COUNT(*) over the whole table is 8 while COUNT(views) is 7. |
| COUNT(column) | Counts the rows where that column is not NULL. Deck wording: counts only non-NULL. If the column is NOT NULL in the schema, COUNT(column) equals COUNT(*): in the youtube_video schema channel is NOT NULL, so COUNT(channel) is always the row count. | COUNT(column) | The question asks how many records have a value recorded for that column, for example how many videos have a likes value. Pack answer on its dataset: COUNT(likes) is 6 out of 8 rows, because two likes values are NULL. | Using COUNT(*) when the question is how many values exist, which counts rows whose value is missing. Also forgetting the NOT NULL shortcut in reverse: for a nullable column the two counts differ, for a NOT NULL column they cannot. |
| COUNT(DISTINCT column) | Counts the distinct non-NULL values in the column. Duplicates collapse before counting, and NULLs are not counted. Pack example: COUNT(DISTINCT channel) on the whole table is 3. | COUNT(DISTINCT column) | The question asks how many different values there are, for example how many distinct channels, or how many distinct categories a channel posts in (COUNT(DISTINCT cat_id) grouped by channel). | Using COUNT(column), which counts rows with a value and so counts the same channel once per video, or using COUNT(*), which counts rows. Neither answers a how many different question. |
| SUM and NULL handling | SUM ignores NULLs. A NULL is skipped, it is not treated as 0 and it does not poison the total. Pack worked value: SUM(likes) for DataDen is 4900, from 4000 plus 900, the NULL likes row contributes nothing. If every value in the set is NULL, SUM returns NULL. | SUM(column), over the non-NULL values only | Any total over a column that can contain NULLs, for example total views per channel where one video has views NULL: that video adds nothing to the total but its row still exists for COUNT(*). | Treating a NULL as 0 in hand calculation, or assuming one NULL makes the whole SUM come out NULL. Neither happens: NULLs are simply skipped. |
| AVG and NULL handling | AVG ignores NULLs in both the sum and the divisor. Deck annotation on the global aggregate example: NULL values ignored. Pack rule in formula form below. Pack worked value: AVG(views) for NullNotes is 60000, from one non-NULL value of 60000 and one NULL. If every value is NULL, AVG returns NULL. | AVG(column) = SUM(column) / COUNT(column). The divisor is the count of non-NULL values, never COUNT(*). | Any average over a nullable column, for example average views or average likes per channel where some rows have NULL. | Dividing by COUNT(*) by hand: on the pack example that gives 60000 / 2 = 30000, exactly half the correct 60000. This is the single most tested NULL trap in the pack. |
| Clause order: writing order vs execution order | Two different orders, and holding both is the skill. You write the query in writing order, but the database runs it in execution order, and several rules (no aggregates in WHERE, no aliases in WHERE) are just execution order applied. Plan queries in execution order. | Writing order (Lecture 4, complete): SELECT, FROM, JOIN, ON, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. Execution order: FROM, JOIN and ON, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT. | Any question asking in what order clauses are written, in what order they run, or why a query fails with an alias or aggregate in the wrong clause. | Assuming writing order and execution order are the same list. Consequences of the real execution order: column aliases are created in SELECT, so they work in ORDER BY but not in WHERE or GROUP BY (PostgreSQL bends the GROUP BY point, Rosario rule is to stick to the standard and use full column names there). Table aliases are different: they are defined in FROM and JOIN and can be used anywhere. |
| GROUP BY discipline | GROUP BY forms the groups that aggregates are computed over, one output row per group. The group can be a single column or multiple columns. In SELECT, grouping columns come first, then the aggregated columns. | GROUP BY <full column names>. Full discipline in the Rosario rules below. | Any per group question: average GPA by major, total views per channel, count per category. Also GROUP BY with no aggregate gives a deduplicated list, equal to SELECT DISTINCT on the grouping columns (pack). | Selecting a bare column that is neither grouped nor aggregated. Deck error, verbatim in substance: column must appear in the GROUP BY clause or be used in an aggregate function. Example: selecting id or title while grouping by major or channel fails, because the database would have to guess which row's value to show. There is no exception to this rule in the decks. |

## Rosario rules (Lecture 3, the evolving list, plus the Lecture 3 quiz rules)
- Never SELECT *. Write out the columns you want to fetch. Deck reasons: schema drift, performance, overfetch, and ambiguous columns after joins.
- In ORDER BY, use column names, not numbers.
- Use full column names in GROUP BY, not indexes.
- Do not use column aliases in HAVING.
- When there is an aggregate function and a GROUP BY, everything in the SELECT must be in an aggregation function or in the GROUP BY. No exceptions are taught in the decks.
- In SELECT, groups come before aggregated columns.
- Use WHERE for conditions on individual rows and HAVING for conditions on groups.

## Full worked example that uses the whole matrix (Lecture 3 deck exercise)
Prompt: return the undergraduate majors that have an average GPA below 3.5, ordered by average descending, top 2. Each clause does one job in execution order: WHERE keeps undergraduate rows, GROUP BY forms majors, HAVING keeps groups whose average is below 3.5, ORDER BY uses the SELECT alias (allowed, because ORDER BY runs after SELECT), LIMIT takes 2.

```sql
SELECT major, AVG(gpa) AS average
FROM bruinbase
WHERE career = 'UG'
GROUP BY major
HAVING AVG(gpa) < 3.5
ORDER BY average DESC
LIMIT 2;
```
