## Principle 1: Data is modeled as relations with keys before it is queried (Lectures 1 to 2)
- Principle: A relational database is a collection of relations, implemented as tables. Each row is a tuple: one transaction, record, or data point. Each column is an attribute, common to all rows, with a type and a domain of legal values, in the same order across rows. A column can hold NULL, which means unknown or missing. The overall design of a database, or of a relation, is its schema. Languages (Lecture 1 and 2 decks): DDL defines, DQL queries (most of the quarter), DML manipulates, with DCL and TCL named only.
- Conditions, the key definitions (Lecture 2 deck):
  Superkey: any set of columns that uniquely identifies each row.
  Candidate key: a minimal superkey. Drop any column from it and it no longer identifies each row.
  Primary key: the one candidate key chosen for the table. It is the single column, or the simplest set of columns, that uniquely identifies each row. There is only one per table and no part of it can contain NULL. A primary key with business meaning is a natural key; a column created only for uniqueness is a surrogate key.
  Unique key: a candidate key not chosen as the primary key, enforced as unique. Unlike the primary key it can contain NULL values, and a table can have many unique keys.
  Foreign key: a column, or set of columns, in the referring (child) table whose values must exist in the referred (parent) table. It maintains referential integrity. It references a unique key in the parent, not necessarily the primary key. A multi column foreign key is a composite foreign key, and all its columns together must match the same combination in the parent.
  Deck examples: in the Video table, {video_id} is a candidate key and the primary key; {video_id, title} is a superkey but not a candidate key.
- Procedure: Build the parent before the child, because a foreign key value must already exist in the parent: the deck's insertion rule is that a video must exist before any comments on it can be recorded, and inserting a comment with a non-existent video_id violates referential integrity. Updates and deletes on a parent key orphan the child rows unless the schema says CASCADE (also update or delete the matching child rows) or SET NULL (replace the child foreign key with NULL and end the relationship). DDL procedure for a table (Lecture 2 deck): column_name column_data_type [NOT NULL] [DEFAULT value_or_function]; single column primary and foreign keys can be written inline, multi column keys are specified at the end of CREATE TABLE. The youtube_video build in the deck: video_id CHAR(11) PRIMARY KEY, channel CHAR(24) NOT NULL with FOREIGN KEY (channel) REFERENCES youtube_channel(channel_id), cat_id SMALLINT DEFAULT 0, views BIGINT DEFAULT 0 (BIGINT because popular videos exceed the INT range), post_date TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP. Schema diagrams: a box per table, primary key attributes underlined, an arrow from each foreign key in the child to the unique key in the parent.
- Failure modes: Picking a non-minimal set as the key (a superkey treated as a candidate key). Putting NULL in any part of a primary key. Inserting a child row before its parent exists, or updating or deleting a parent key and orphaning child rows. Confusing key jobs: a foreign key exists to impose referential integrity, and whether it can also serve as a join key is a separate matter (Lecture 4 deck: foreign keys can be join keys, but the purpose of a foreign key has nothing to do with joins). Data type traps from Lecture 2: demoting a type and truncating data (promote only), comparing floating point values as if exact, and using TIMESTAMP without a time zone where TIMESTAMPTZ is the deck's advice.

## Principle 2: A query fetches rows from one table in a fixed clause discipline (Lecture 3, first half)
- Principle: A SELECT statement queries one or more relations and changes nothing: results are ephemeral unless written to a file or a new table. SELECT extracts columns, WHERE filters out rows, and WHERE does so before SELECT. Transformation functions and arithmetic apply to each row independently and columns can be renamed with aliases.
- Conditions: Writing order: SELECT, FROM, WHERE, ORDER BY, LIMIT (Lecture 3 form; joins extend it in Principle 4). Execution order: FROM, WHERE, SELECT, DISTINCT, ORDER BY, LIMIT. Column aliases are created in SELECT, so they are available in ORDER BY but not in WHERE or GROUP BY. DISTINCT is distributed across all columns in the SELECT, not applied column by column. ORDER BY defaults to ascending; in PostgreSQL, NULL sorts above every value, so a DESC sort puts NULLs first unless NULLS LAST is written. WHERE tests use =, >, <, >=, <=, != (or <>), AND, OR, IN, NOT IN, IS NULL, IS NOT NULL.
- Procedure: Plan in execution order, not writing order. Deck template: SELECT col1, col2 AS new_col2, f(col3) AS new_col3, ... FROM tablename WHERE <predicate> ORDER BY column_or_set_of_columns. Worked deck cases: the youtube_video fetch computing millions_views and pct_liked per row, and the tinybase fetch sorting by gpa DESC, lastname, firstname with LIMIT 3 after removing NULL gpa rows in WHERE.
- Failure modes: Using SELECT *, banned by the Lecture 3 quiz rules, for schema drift, performance, overfetch, and ambiguous columns after joins. Ordering by column sequence numbers instead of column names, also banned. Using a SELECT alias in WHERE, where it does not exist yet. Expecting SELECT to change the table: it never does. Transcribing a query into a verbatim transcript style with no filtering thought is the Lecture 3 notes trap generally: capture the predicate and the sort keys, not just the column list.

## Control flow branch (Lecture 3, between Principles 2 and 3)
- Principle: Output values can be computed conditionally inside the query. CASE is the SQL standard conditional, in two forms. NULLIF returns NULL on invalid data, based on an equality.
- Conditions: Simple CASE matches one column against exact values (CASE level WHEN 'UFR' THEN 'Freshman' ... ELSE 'Unclassified' END AS new_level, from the bruinbase deck example). Searched CASE tests arbitrary conditions in order (CASE WHEN level IN ('UFR', 'USO', 'UJR', 'USR') THEN 'Undergraduate' WHEN level IN ('GMT', 'GD1', 'GD2') THEN 'Graduate' WHEN level = 'CHN' THEN 'Chancellor' ELSE 'Unknown' END AS new_career). NULLIF(a, b) returns NULL when a equals b and a otherwise. A CASE column must be named with END AS, or PostgreSQL names it "case" and two CASE columns collide.
- Procedure: Put the CASE or NULLIF expression in the SELECT list as a computed column. Deck use of NULLIF: CAST(likes * 100.0 / NULLIF(likes + dislikes, 0) AS DECIMAL(5,2)) AS pct_liked, where NULLIF turns a zero denominator into NULL so the row yields NULL instead of an error.
- Failure modes: Reaching for simple CASE when the condition is a range or spans several columns, which needs searched CASE. Using NULLIF as if it were a general if: it tests one equality only. Trying an IF() function: PostgreSQL has none in queries.

## Principle 3: Aggregation collapses rows into groups, and the grouping rules are strict (Lecture 3, second half)
- Principle: Aggregation functions run across groups of rows, where a transformation function runs row by row. Without GROUP BY, an aggregate summarizes the whole table as one set. With GROUP BY, rows are grouped by one column or several, one output row per group, and in SELECT the grouping columns come first, then the aggregated columns. WHERE filters rows, HAVING filters groups.
- Conditions: The counting and NULL rules. COUNT(*) counts all rows. COUNT(column) counts only non-NULL values, so it equals COUNT(*) when the column is NOT NULL. COUNT(DISTINCT column) counts distinct non-NULL values. MIN, MAX, and AVG ignore NULL values (deck annotation), and SUM ignores NULLs as well (replacement pack, with worked values). AVG equals SUM(column) divided by COUNT(column), never COUNT(*). Full clause orders with aggregation: writing order SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT; execution order FROM, WHERE, GROUP BY, HAVING, SELECT, DISTINCT, ORDER BY, LIMIT.
- Procedure: Deck worked path on bruinbase: group rows by major, compute AVG(gpa) per group (Comp Sci 2.8, Math 3.75, Stats 3.1), then filter groups with HAVING AVG(gpa) < 3.5. Full deck exercise combining every clause: SELECT major, AVG(gpa) AS average FROM bruinbase WHERE career = 'UG' GROUP BY major HAVING AVG(gpa) < 3.5 ORDER BY average DESC LIMIT 2. Pack worked path on youtube_video: WHERE privacy = 'public' first, then GROUP BY channel, then COUNT(*) per group, and AVG(views) per channel with HAVING AVG(views) > 70000, where NullNotes fails at 60000 because its NULL views row is skipped by AVG.
- Failure modes: Selecting a column that is neither grouped nor aggregated: the deck error is that the column must appear in the GROUP BY clause or be used in an aggregate function, because inside one group that column holds many values and the database will not guess. Putting an aggregate condition in WHERE (WHERE COUNT(*) > 2 fails, aggregates do not exist yet) instead of HAVING. Using a SELECT alias in HAVING instead of repeating the full aggregate. Using indexes or aliases in GROUP BY instead of full column names. Dividing by COUNT(*) when computing an average by hand: the pack's NullNotes trap, 30000 instead of 60000. Note on sources: the replacement pack teaches one extra PostgreSQL behavior here, grouping by a primary key allowing other columns of that table in SELECT. The Lecture 3 deck states the rule with no such exception, and the deck rule is the one this tree teaches. See the contradiction note at the end of this file.

## Principle 4: Tables and result sets combine, and the combining is written one explicit way (Lecture 4)
- Principle: A join ties together data spread across tables, based on common attributes called the join key. The join key does not need to enforce uniqueness; uniqueness can come from a PRIMARY KEY or UNIQUE constraint, and referential integrity applies only when the columns are marked FOREIGN KEY. Mechanically, an inner join forms all pairs of rows (the Cartesian product) and then filters the pairs on the join condition. Joining makes output wider (more columns). UNION and UNION ALL instead stack rows, making output taller.
- Conditions: Relationship cardinality controls the row count: 1:1, 1:M, and M:M, with duplicate join keys multiplying output rows because a row matches every matching row, not just the first. Inner equi join: only rows whose join key values match in both tables, no match, no row (Lecture 4 wording). Inner non-equi join: the ON condition contains a comparator that is not =, and a row is kept when it satisfies the condition. Cross join: the full Cartesian product with no condition, taught as an antipattern with nearly no legitimate use, and using one plus a WHERE filter receives no credit. UNION removes duplicates when stacking, UNION ALL keeps them; duplicates are allowed in either output because a result set is not a table. Writing order with joins: SELECT, FROM, JOIN, ON, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT. Execution order adds the join at the front: FROM, JOIN and ON, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT (with DISTINCT after SELECT per Lecture 3).
- Procedure: Rosario's join writing strategy, in execution order: do not panic; start with FROM, write the JOIN, then the ON condition with special care, then WHERE, then GROUP BY, then HAVING, then SELECT with proper aliases, then ORDER BY, then LIMIT if needed. Deck canonical equi join: SELECT R.A, B, C, D FROM R INNER JOIN S ON R.A = S.A, with A qualified because it exists in both tables, while B and C need no qualification because each exists in only one table. Deck non-equi shape: score percentages matched against grade bands by minimum and maximum. A column used in ON, WHERE, or GROUP BY does not have to appear in SELECT. To join another table, add another JOIN ... ON clause.
- Failure modes: Every join antipattern from Lecture 4. NATURAL JOIN: the database picks the join columns, the condition is invisible, and adding a same named column to both tables silently changes the result or degrades it into a cross join. The implicit comma join (tables listed in FROM with the condition in WHERE): not accepted. USING: on exams the condition must be stated explicitly, so JOIN ... ON is required. A join condition that is not tight enough, producing a Cartesian join, runaway join, join explosion, or fanout that can exhaust memory and crash the server. Failing to qualify a shared column name, which is ambiguous. Outer joins are not a failure mode here, they are simply not yet covered: they are Lecture 5 material, and Lecture 4 only names them in the classification chart and a footnote saying they add back unmatched rows next lecture.

## Contradiction note (deck vs replacement pack, resolved in favor of the deck)
The replacement pack's Topic 5 teaches that PostgreSQL allows selecting other columns of a table when grouping by that table's primary key (functional dependency), and its recitable summary repeats it as the sole exception to the grouping rule. The Lecture 3 deck states the rule with no exception: when there is an aggregate function and a GROUP BY, everything in the SELECT must be in an aggregation function or in the GROUP BY, and its worked error example fails a query on exactly that basis. These files follow the deck, as Rosario's stated quiz and exam rule. On a quiz, do not rely on the primary key exception.
